The one architectural rule

Attendance is an event, not a state.

Verification never asks whether a wallet still holds the badge. It asks whether that wallet ever accepted a badge this issuer minted under this taxon. The attendee's NFTokenAcceptOffer hash is the attendance record, and the ledger keeps it forever. Walk the seven steps below, burn the badge at step 6, and watch the proof survive at step 7.

          Where the money can leak, and what stops it
          
    
            
  • The slot is taken before the spend. UNIQUE(event_id, address) is the mint guard. Six retries would otherwise mint six badges and lock 1.2 XRP in six open offers. Press Claim badge a second time: you get 200 with reusedExistingOffer: true, not a second mint.
    • 
            
  • Sponsorship is booked before the money moves. reserve() then Payment then confirm(). Check-then-pay-then-record pays N times under concurrency and records one.
    • 
            
  • Offers are lazy, one per attendee. Each open offer locks 0.2 XRP; pre-creating 100 locks 20 XRP at once.
    • 
            
  • Every offer sets Destination. Without it anyone watching the ledger can accept the offer and take the badge.
    •

4

      

        

          
Confirm — re-derive, then index

          POST/events/{eventId}/claims/{offerId}/confirm
        

        
attendee → api → xrp ledger → attendance index

        

          A client saying "I claimed it" is not evidence that it did. The API pulls the transaction
          off the ledger and runs five checks. All five, or no row is written — a failure is
          422 with the failing check named, and nothing is indexed. The offer id in the
          path is only a correlation hint; what gets stored is the offer the accept transaction
          actually consumed, read from the chain.
        

        

          
          
          
Editable on purpose. Change one character and confirm again to watch transactionFound fail and the write be refused. Steps 5 and 7 verify whatever hash sits in this field.

      Phase 4
      
Destroy the badge

      The point of the whole project is what happens next.
    


    
    

      
6

      

        

          
Burn the badge

          POST/demo/burn
        

        
issuer → xrp ledger · destructive · irreversible

        

          Badges are minted with tfBurnable, so a badge issued in error can be revoked.
          This destroys the NFToken. After it lands, account_nfts for the attendee
          returns 0 — the query that looks like it answers "did they attend" and
          returns zero for someone who demonstrably did.
